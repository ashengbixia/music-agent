# AI 使用说明

本项目由本人主导需求把关、方案取舍、本地集成和验收推进，使用 AI 编程助手辅助代码编写、排错与测试。本人以测试题规定的创作流程为基础，持续检查实现是否贴合需求，并根据实际运行结果调整方案。

开发中的工作重点，是将模型生成能力落实为可本地运行、设有人工审核关卡、有版本记录、可恢复失败步骤、可校验交付文件的工程流程。

## 一、本人负责的核心工作

| 工作方向 | 本人承担的工作与具体决策 |
| --- | --- |
| 需求与范围把关 | 多次对照测试题核对实现，明确以本地发行物料包为终点，控制项目规模，不引入额外 Web 服务或发行平台对接。 |
| 架构与开发节奏 | 要求从小步骤搭建，再按实际需要拆分模块；指出主入口逻辑堆积问题，推动 CLI、模型客户端、审核、存储与打包职责分离。 |
| 输入与数据设计 | 坚持兼容题目提供的 brief，否定额外手填发行资料的方案；明确项目编号、创作项目名和歌曲标题分别保存。 |
| 实现检查与问题反馈 | 指出重复读取、重复校验和固定稿件路径等问题；针对文件创建模式、哈希、运行编号和时间格式逐项讨论并确定使用方式。 |
| 本地集成与流程验证 | 在本地执行创作、审核和恢复命令，提供真实错误输出，结合产物检查推动问题定位与修正。 |
| 验收与交付推进 | 要求重新逐项复查需求，推动补齐异常测试、运行报告、交付文档及环境配置，明确区分功能跑通与完整交付。 |

其中几项实际调整体现了本人对方案的持续把关：

- **减少不必要的输入和模型请求。** 发行资料最初准备通过额外文件手填，本人指出这会增加题目未要求的输入负担；项目名称也不应直接复用项目编号或另开一次模型请求，最终在原作词请求中一并生成。
- **推动代码按职责组织。** 在发现逻辑集中于 main.py，以及打包函数之间重复读取数据后，提出模块拆分和数据复用要求，逐步形成独立的业务模块与打包快照流程。
- **把验收推进到异常场景。** 正常路径跑通后，本人继续要求对照完整题目补测。复查发现歌词审核后报告滞后、音频元数据缺失仍能导出等问题，随后完成修正及回归验证。

这些工作贯穿需求、实现和验收，形成了从方案评估到问题修正的持续反馈。

## 二、本人和 AI 的协作方式

### 1. 开发阶段

本人提出需求、审阅方案、确定修改方向，并根据本地运行结果持续反馈。前期主要按 AI 提供的带注释代码和步骤在本地实施；后期在本人明确授权后，由 AI 直接写入部分代码、测试和文档。

AI 编程助手主要参与以下工作：

- 提供模块设计建议、Python 代码初稿、提示词、Schema 和中文注释。
- 根据本人反馈调整实现，辅助定位接口、状态和文件处理问题。
- 编写自动化测试，在本机执行测试并报告结果。
- 根据实际过程整理 README、环境配置、开发日志和本说明。

代码中包含 AI 生成和协助修改的内容；本人贡献主要体现在需求把关、方案评估、设计决策、本地实施、问题反馈和验收推进。双方按任务分工协作，关键方案和开发节奏由本人决定。

### 2. 项目运行阶段

| 内容 | 生成或处理方式 |
| --- | --- |
| 任务计划 | DeepSeek 生成，程序校验字段及固定阶段顺序。 |
| 项目名、歌名和分段歌词 | DeepSeek 生成；拒绝后根据旧稿与人工反馈修订。 |
| 作曲方案 | DeepSeek 生成 BPM、调性、段落时长、编曲说明和 handoff，程序校验结构与时长。 |
| 音频 | Python 标准库合成本地 mock 测试音，不包含真实演唱或完整编曲效果。 |
| 三张纯色封面 | 程序生成的 PNG 占位图。 |
| 状态、哈希、版本、调用记录和物料包 | 本地程序根据实际输入、响应与文件整理，模型不能直接决定审核通过。 |

本人通过 CLI 执行人工审核确认。模型输出、测试中模拟的审核操作与实际人工审核分别记录。

## 三、已完成的检查与验证

验证结合本人本地运行反馈、代码复查，以及 AI 编程助手在本机执行的自动化测试进行。最近一次完整测试结果为 **202 项通过**。

主要检查内容包括：

- **需求与输出校验：** brief 缺项、类型、时长和平台冲突，以及计划、歌词、作曲方案的结构与业务约束。
- **审核和版本保护：** 歌词未审核不能作曲，音频未审核不能导出 ready 包；歌词修订保留旧稿，审核绑定具体版本和哈希。
- **失败处理：** 超时、429、非法响应、空音频、损坏音频、检查点恢复和打包提交窗口中断。
- **重复执行与安全边界：** 同需求复用、已审核音频防覆盖，以及提示注入不能绕过人工审核。
- **交付完整性：** 物料包文件与哈希、音频实际参数、审核记录、CLI 完整流程和运行报告同步。

测试采用模拟接口和临时目录，不调用真实 API，不修改已有歌曲产物。两份正常题目 brief 均已通过完整模拟流程；异常 brief 的缺失和冲突字段也有拦截测试。

发行物料通过文件完整性、哈希、音频参数和审核绑定进行检查。运行报告、模型调用记录和作曲交接清单按同一次运行关联，便于追溯生成与审核过程。

## 四、结果边界

自动化测试验证的是已覆盖场景中的工程行为。歌词主题贴合度、原创要求和实际音乐效果仍需人工判断；mock 测试音不等同于正式歌曲，程序整理的制作声明也不等同于原创性鉴定。

运行环境通过 environment.yml 管理。真实创作使用实际配置的 DeepSeek，自动化测试使用模拟接口，分别验证创作流程与程序行为。
