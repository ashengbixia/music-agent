# 音乐创作 Agent 开发日志

开发开始日期：2026-10-29。

记录更新至：2026-10-30。

本文根据实际开发对话、当前代码和本地产物整理。早期阶段没有逐步记录提交时间，因此按日期和开发阶段回顾，不虚构具体时刻。

阅读说明：前文保留各开发阶段当时的设计与排错背景，后文记录后续修正。最终使用方法以 README 和本地演示与命令手册为准，交付物入口以 项目交付说明.md 为准；不必按本日志中的历史命令重新执行项目。

## 一、项目目标与开发方式

项目实现本地命令行音乐创作流程：读取歌曲需求单，由 DeepSeek 生成计划和歌词，人工审核歌词后生成作曲方案及 mock 音频，再经过音频审核，导出可校验的本地发行物料包。下游发行 Agent 和发行平台调用不在实现范围内。

开发方式从直接生成代码调整为：AI 说明设计、提供带注释的代码和修改位置，由开发者理解后手动修改、运行并反馈结果；开发者明确要求“帮我改”“帮我写”或“写入”时，再由 AI 直接修改文件并验证。依赖安装优先提供 conda 命令。项目以逐步跑通流程为主，不引入 FastAPI 或网页服务。

## 二、2026-10-29：需求梳理与基础搭建

### 1. 明确范围，重新控制项目规模

阅读《音乐.md》，确认核心交付是主 Agent、作词子 Agent、作曲/音频子 Agent，以及人工审核、产物校验和本地物料导出。

初期目录拆分较多，开发者提出从头搭建，避免还未理解流程就一次性创建大量模块。自动清空操作曾被安全审核拒绝，不能将该操作记录为已自动完成。随后在整理后的工作区中从最小入口开始搭建。

### 2. 实现需求单读取

新增 `main.py` 和 `brief.json`，支持：

```text
python main.py run --brief brief.json
```

基础校验包括 JSON 顶层为对象、项目编号及主题等字段为非空文本、时长为正整数。明确排除将布尔值当作整数秒数的情况。

按照开发者要求，为模块、函数、参数、返回值、异常及关键逻辑补充中文注释。

### 3. 接入 DeepSeek 计划生成

主 Agent 请求 DeepSeek 输出 JSON 任务计划，固定阶段为：

```text
lyrics → lyrics_review → audio → audio_review → package
```

通过三层约束控制输出：系统提示词及示例、接口 `response_format=json_object`、程序解析和业务校验。程序检查项目编号、字段、步骤数量和顺序，拒绝缺失审核阶段的计划。

此时生成的计划只是任务数据，尚不会自动执行。后续通过提取步骤中的 `description`，与 brief 一起传给对应子 Agent，建立计划与执行之间的连接。

### 4. 从单文件调整为按职责拆分

随着接口调用加入，全部逻辑堆在 `main.py` 中不便理解和维护。按开发者反馈，拆出需求单处理和计划生成模块，再提取公共 DeepSeek 客户端，供后续子 Agent 复用。

没有一次性创建完整目标目录中的所有模块，而是功能需要时再添加。

## 三、2026-10-29：作词、审核与状态管理

### 1. 作词子 Agent

新增 `agents/lyricist.py` 和 `schemas.py`，使用 `jsonschema` 校验输出。歌词包含歌名、按演唱顺序排列的段落、每段情绪及歌词行。

`workflow.py` 负责生成计划、提取作词任务、调用作词子 Agent 和保存产物。流程生成歌词后停在 `lyrics_ready`，等待人工审核。

### 2. 保存版本与文件指纹

状态中加入 `lyrics_version` 和 `lyrics_sha256`。哈希是实际文件字节的指纹，原歌词文件仍然保留。

生成时保存旧哈希，审核或使用时重新计算当前哈希，两者不一致则阻止继续。该机制用于检查内容是否变化，不代表文件和状态同时被人为修改时仍能防篡改。

开发中还明确了两个文件操作细节：`open(..., "x")` 创建新文件并拒绝覆盖；`indent=2` 仅影响 JSON 的换行与缩进，不改变数据。

### 3. 人工审核与项目查找

新增 `review.py` 和 `storage.py`，提供：

```text
python main.py approve --project song_001 --stage lyrics --reviewer "阿圣"
python main.py status song_001
```

审核通过前检查待审核状态、歌词版本和文件哈希，记录审核人、结论、版本、哈希和时间，将状态更新为 `lyrics_approved`。状态更新采用临时文件写完后替换的方式，降低写入中断损坏旧状态的风险。

项目优先通过 `project_id` 查找。现有存储结构仍是 `outputs/run-<UUID>/`；同一项目有多次运行时，使用可选 `--run` 明确选择，不自动挑选某一次审核。

曾讨论将目录改成固定项目目录，但开发者认为修改范围过大，因此未采用该重构。当前实际代码中的 `load_state` 仍接收运行目录，与入口调用一致。

### 4. 调整审核时间

最初保存 UTC ISO 时间，开发者认为不便阅读。经讨论，最终改为直接保存易读的北京时间，例如：

```text
2026-10-29 17:28:47（北京时间）
```

## 四、2026-10-29：作曲方案与 mock 音频

### 1. 实现 mock 音频客户端

新增 `clients/mock_music.py`，通过标准库生成单声道、16 位 PCM、22050 Hz 的 WAV。逐秒写入固定 440 Hz 测试音，输出格式、时长、采样率、声道和 SHA-256 等元数据。

生成并检查了 `outputs/mock_test.wav`：3 秒，132344 字节，可正常识别并完整读取音频数据。

mock 音频用于验证文件与流程，不包含演唱，也不实际呈现模型生成的编曲方案。

### 2. 实现作曲子 Agent

新增 `agents/composer.py`，扩展作曲方案 Schema。输出 BPM、调性、分段时长、编曲说明和 handoff。

程序除 Schema 校验外，还要求作曲段落数量、名称和顺序与歌词一致，所有段落时长之和等于 brief 中的目标时长。

### 3. 接入 resume

新增命令：

```text
python main.py resume song_001
```

这一阶段先实现从 `lyrics_approved` 继续，重新核对审核结论、版本和歌词哈希，读取保存的 brief 和计划，生成 `composition-v001.json`、`audio-v001.wav`，成功后更新为 `audio_ready`。10 月 30 日再扩展初始生成和歌词修订的恢复分支。

### 4. 排查需求单快照缺失

早期运行目录没有保存 `brief.json`，导致 resume 出现文件不存在错误。之后在新建流程中增加 brief 快照保存，旧运行需要补回当时实际使用的需求单。不能未经核对就使用已经改过的新 brief 继续旧项目。

### 5. 排查 DeepSeek 未正常结束

作曲阶段两次返回“DeepSeek 响应未正常结束”。原代码把所有非 `stop` 的结束原因合并成同一条错误，无法确定究竟是截断还是其他原因。

当前已将 `max_tokens` 从 2048 提高到 8192，并在异常中显示 `finish_reason` 和 `usage`。曾建议关闭思考模式，但当前代码尚未加入该参数。

后续本地产物已显示作曲和音频生成成功。不过未保留之前失败响应的具体结束原因，因此不能把“达到 token 上限”记录为已证实的根因。

## 五、2026-10-29：音频审核与发行物料包

### 1. 接入音频人工审核

新增 `approve_audio()`，命令行审核阶段扩展为 `lyrics|audio`。人工试听测试音频并查看作曲方案后，通过以下命令确认：

```text
python main.py approve --project song_001 --stage audio --reviewer "阿圣"
```

程序核对歌词审核、当前歌词哈希、作曲方案哈希、音频版本和哈希，并完整读取 WAV 采样数据，检查格式、时长、采样率及声道是否与记录一致。审核通过后进入 `audio_approved`。

音频审核记录同时绑定歌词、作曲方案和音频版本，防止其中一个产物变化后继续沿用旧审核。

### 2. 修正发行信息来源

最初提出让开发者手动在运行目录创建 `release_info.json`，填写艺人名、版权声明和封面路径。开发者指出 brief 由测试方提供，不应为正常运行强制增加输入字段，也不应要求手动补写输出目录。

重新核对测试题后，最终采用：

| 信息 | 来源 |
| --- | --- |
| 项目编号 | brief 中的 `project_id` |
| 歌曲标题 | 作词输出的 `title` |
| 创作项目名 | 作词输出的 `project_name` |
| 封面 | brief 原有的 `cover_placeholder_path` |
| 版权/原创声明 | 程序基于当前 AI 辅助创作和 mock 音频制作方式整理 |
| 审核记录 | 已保存的歌词、音频审核结果 |

曾考虑直接以项目编号充当项目名，或单独调用模型命名，均被开发者指出不合适。最终将 `project_name` 加入歌词 Schema 和作词提示词，在同一次模型请求中生成并保存，不增加额外命名请求。

声明记录原创要求和制作方式，不把模型自称原创当作原创性鉴定。当前声明逻辑仅适用于已有的本地合成 mock 音频实现。未采用手动 `release_info.json` 方案。

### 3. 准备封面与包内文件

生成三张 1024×1024 的纯色 PNG 占位封面，分别保存在 `fixtures/covers/cover_01.png`、`cover_02.png`、`cover_03.png`。第一份 brief 继续使用原有的 `cover_01.png` 路径。

新增 `packaging.py`，收集发行信息，检查缺项、源文件哈希和审核绑定，并使用 Pillow 校验封面 PNG。将结构化歌词转换成 `lyrics.md`，保留歌词 JSON 作为审核源文件。

明确区分：审核记录绑定原始 `lyrics.json` 的哈希，包内 manifest 则另外记录转换后的 `lyrics.md` 哈希，两者不能混用。

### 4. 消除重复读取与校验

开发者发现打包主函数及子函数反复读取状态、歌词和其他产物。将流程调整为一次加载快照，再由不同函数分别检查资料和审核一致性。

当前职责划分：

- `load_package_snapshot()`：读取状态、版本和源文件字节，解析 brief 与歌词。
- `check_release_info(snapshot)`：检查发行资料和封面路径。
- `validate_approved_assets(snapshot)`：校验源文件哈希、版本和审核绑定。
- `prepare_package_files(snapshot)`：复用已读取数据，准备六个包内文件的字节内容和发行信息。
- `verify_package_files()`：读取实际导出的目标文件，核对字节数和哈希。

导出前验证源数据、导出后验证目标文件分别检查不同对象，因此保留；去掉的是中间重复读取同一份源文件的操作。

### 5. 接通 export 并验证结果

新增本地导出命令：

```text
python main.py export --project song_001
```

先写临时目录，校验六个包内文件，再提交正式 `release-package`，随后将项目状态更新为 `package_ready`。后续进一步调整为：临时 manifest 先写 `needs_info`，完整校验通过后才改为 `ready` 并提交目录。重复导出同一输入时，比较 manifest 元数据并验证已有包，复用已有首版，不覆盖内容。

开发者实际运行导出后，已检查规定的七个文件、六个物料文件大小与哈希、brief 哈希、歌词审核源文件哈希、两份审核记录、作曲方案与音频的审核绑定。结果均一致。WAV 为完整的 210 秒、22050 Hz、单声道音频，物料包为 `ready`，项目为 `package_ready`。

## 六、2026-10-30：补齐异常处理、恢复和运行记录

### 1. 完善需求校验与重复运行规则

重新对照测试题，补上受众、平台列表、主平台归属、采样许可类型，以及文字时长与秒数一致性等校验。缺封面允许先进入创作，导出时必须报告缺项；受众缺失或时长、平台冲突则在请求模型之前拒绝。

新增 `calculate_brief_fingerprint()`，对规范化 JSON 计算内容指纹，忽略字段顺序和排版差异。同项目编号、同一需求重复运行时复用已有目录，不再请求模型；同编号但需求变化、快照变化或存在多个候选运行时明确报错。该内容指纹与发行包中按原始 brief 文件字节计算的哈希用途不同。

### 2. 实现网络重试和作曲检查点

将作曲业务校验提取为 `validate_composition()`，新生成和恢复已有方案都要检查 Schema、段落顺序和总时长。作曲方案已成功、音频失败时，下一次 `resume` 校验并复用原方案，只恢复音频步骤。

DeepSeek 客户端对超时、连接异常及 HTTP 429、500、502、503、504 进行有限重试，默认最多三次请求，重试间隔为 1 秒、2 秒；401、403 和非法 JSON 不自动重试。音频阶段失败则记录错误并停留在原审核状态，通过再次 `resume` 重试，不能带着失败结果向后推进。

### 3. 扩展初始生成和中断恢复

首次模型请求前先保存 brief 快照和 `new` 状态，保证计划生成失败后仍能按项目编号找到运行目录。计划成功、歌词失败后恢复时复用已保存计划；产物已完整提交、检查点尚未登记就中断的情况，也通过结构与哈希校验恢复。

歌词修订、作曲和音频生成前保存任务记录，绑定输入及目标版本，避免把其他输入或不明来源文件当作本次结果。任务输入变化、已登记文件丢失、哈希不符或结构不合法时停止，不静默覆盖或重新生成。

完整且来源匹配的未审核音频可以复用；当前任务留下的空文件或截断 WAV 会保留为带 `.failed-` 标记的故障文件，再生成有效音频。已审核音频及没有生成记录的已有音频不能被恢复逻辑覆盖。

### 4. 接通歌词拒绝与多版本修订

新增歌词拒绝命令，例如：

```text
python main.py reject --project song_001 --stage lyrics --reviewer "阿圣" --feedback "增加毕业场景，副歌更克制"
python main.py resume song_001
```

拒绝时记录审核人、修改意见、歌词版本及哈希，进入 `lyrics_rejected`。恢复时将旧歌词和反馈交给作词子 Agent，生成 `lyrics-v002.json` 等新版本，保留旧稿和拒绝历史。新版本仍需人工审核，不能直接进入作曲。

修订必须保留创作项目名。后续审核、作曲和导出统一使用 `state.json` 中 `lyrics_file` 指向的当前稿件，不根据固定的 `lyrics.json` 或文件名最大序号猜测最新版。

### 5. 保存模型调用记录和作曲交接清单

为计划、作词和作曲请求增加响应记录回调，保存到运行目录的 `model-calls/`。记录包含阶段、目标版本、实际显式发送的生成参数、请求及返回模型、耗时、结束原因、usage 和原始内容摘要、长度及哈希。失败与非法响应也保留对应记录，不记录请求密钥或完整提示词。

调用记录保存的是逻辑请求记录数，不等于包含重试在内的实际 HTTP 次数；收到响应也不等于产物通过业务校验。

作曲和音频完成后生成 `composition-result-v001.json`，列出歌词来源、音乐模型参数、作曲方案与音频的路径、版本、哈希、音频参数和 handoff。明确标记音频仍需人工审核，且是没有真实演唱和编曲效果的 mock 测试音。

### 6. 新增运行报告，并修正审核后报告滞后

新增 `reporting.py`。统一保存状态时，用同一份状态快照生成 `run_report.json`，记录当前进度、版本、哈希、审核结果、失败及恢复历史、物料包信息和模型调用记录引用。相同进度重复保存不重复追加事件；旧项目首次生成报告只记录当前观察到的状态，不补造过去的运行历史。

逐项复查需求时，发现 `approve_lyrics()` 仍自行写状态文件，绕过统一保存函数。临时目录复现结果是：歌词已进入 `lyrics_approved`，报告却仍为 `lyrics_ready`。随后改为调用 `save_state()`，审核命令结束后报告立即同步，并补上成功同步及审核失败不改状态、报告的回归测试。

### 7. 加固发行包校验，并修正音频元数据遗漏

完善导出缺项、快照读取失败、审核绑定、重复导出和已有包损坏的处理。包内任一文件缺失或哈希不一致时，不能保持 `ready`；无法解析的原始 manifest 备份在包外。原件修复后可重新校验，保留原物料包版本和创建时间。源文件损坏与旧包自身损坏分别判断，完整旧包不因源文件异常被直接改写。

复查还发现：从源状态删除音频格式、时长、采样率或声道后，程序仍能导出 `ready` 包。随后增加必需参数、类型、正数及有限值检查，并将参数与实际 WAV 字节比较；源状态和已有 manifest 都要通过校验。

提取 `inspect_audio_bytes()`，让打包阶段复用已经读取的音频快照，不重新读取源 WAV。回归测试同时验证缺字段、非法值、参数与文件不符，以及源音频只读取一次。

## 七、2026-10-30：自动化测试与最终复查

### 1. 从临时验证转为可重复运行的测试

将正常路径和故障场景整理为 pytest 测试文件。测试使用临时目录、模拟 DeepSeek 响应和真实本地 mock WAV，不调用真实 API，也不修改已有歌曲产物。

将题目原样提供的三份需求单加入 `fixtures/briefs/`：两份正常样例，以及一份缺受众、时长冲突、主平台冲突的异常样例。异常样例保留原始错误，测试逐项修复前置错误后，确认后续冲突仍会被拦截。

主要覆盖范围：

| 范围 | 验证内容 |
| --- | --- |
| 需求与计划 | 类型和缺项、时长及平台冲突、固定步骤顺序、删除或替换审核步骤被拒绝 |
| 模型客户端 | 超时及 429 等重试、鉴权失败不重试、非法 JSON、空响应、截断响应与调用记录 |
| 人工审核 | 未审核不能推进、歌词拒绝后修订、旧稿保留、当前稿指针、版本及哈希绑定 |
| 幂等与恢复 | 同需求复用、输入变化拒绝复用、初始生成及修订/作曲提交窗口中断恢复 |
| 音频 | 空文件、损坏及截断文件、参数一致性、失败恢复、已审核文件防覆盖 |
| 物料包 | 缺封面/声明/审核记录、文件缺失或哈希不符、清单损坏、重复导出与修复 |
| 运行报告 | 状态同步、失败历史保留、重复事件去重、原子写入及旧项目不伪造历史 |
| 提示注入 | brief 和模型文字要求跳过审核时，两个程序审核关卡仍然生效 |
